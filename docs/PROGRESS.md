# Rust port progress

Faithful port of [Super Mario War](https://github.com/mmatyas/supermariowar) (C++/SDL2) to Rust + rust-sdl2. Logic mirrors the C++ file by file; parity is checked by differential replay (see `REPLAY.md`).

Scope order: core game + menus + sound, then netplay, level editor, world editor.

## Known C++ issues

- Upstream `5c979393` gave hazard and platform drawing an explicit destination, but the hazards and platform shadows drawn by position in map thumbnails still go to `blitdest`, so thumbnails lack them. The port reproduces this.
- `RandomNumberGenerator::getBoolean(scaleMax, positiveThreshold)` (`get_boolean_threshold`) asserts `positiveThreshold < scaleMax && positiveThreshold >= 0` (`random_number_generator.rs:43`, a `debug_assert!` port of the C++ `assert`). Replay `opt_gameplay` trips it at frame 1209 in a release build with debug assertions. The C++ has the same assert, compiled out in the Release reference, so a debug C++ build would fail it too; the caller passing the bad range is not yet traced.
- The level editor draws a platform's hover preview at `event.button.x/y` after its poll loop, a stale event. SDL2 leaves its poll sentinel there and sdl2-compat the last real event, so the editors poll into a temporary (`poll_event`, `sdl_helpers.rs`) and the post-loop event matches sdl2-compat, which recorded the goldens, on every SDL2 build.

## Deliberate deviations from the C++

Replays without joysticks still match the C++ goldens. `joy_menu`, `joy_game`, `pad_hotplug`, `text_shift` and `osk_pad` exercise these deviations and are checked against Rust goldens (`tools/golden_rust/`, `make_golden.sh` with `RUST_GOLDEN=1`); `parity.sh` marks them "(Rust golden)".

- Stick and D-pad are one control: on a joystick, a binding to a stick 1 direction also fires from the same hat direction and vice versa, in game and in menus (`CPlayerInput::update`). Upstream reads only the bound one, and its defaults bind the stick, so a D-pad-only pad did nothing.
- Players get inputs at every launch (`assign_inputs`, `main.rs`): connected joysticks first, then the right keyboard set (player 1's keyboard bindings), then the left one (player 2's); those players become human. 1 pad: P1 pad, P2 right, P3 left; 2 pads: P1-2 pads, P3 right, P4 left; 3: P4 right; 4: all pads. While the page's touch controls are on, the right keyboard set (the keys they press) goes to player 1 ahead of the joysticks. The first launch with joysticks saves the players' `playercontrol` to `pad_players.txt` in the settings directory; the next launch without joysticks restores it, sets every player back to their own keyboard set, saves the settings and deletes the file. Without that file (no pad history) a launch with no joystick keeps the saved assignment, as upstream. A joystick's bindings belong to it (`inputConfiguration[pad][1]`), so they follow it to whichever player has it; switching a player to the keyboard in Controls takes the first keyboard set no other player has.
- Game controllers, muOS and Android only (`pad.rs`, opted into by `SMW_PAD_TRANSLATE=1`, which only the muOS launcher and the Android manifest set; elsewhere the port reads pads as before and only logs them): a joystick SDL has a game-controller mapping for (its database, `SDL_GAMECONTROLLERCONFIG`, or a built-in mapping for muOS's `muOS-Keys`) is read through that mapping. Its raw joystick events are renumbered through the mapping's binds into a fixed layout (inputs the mapping leaves out are dropped): A, B, X on buttons 0-2 (jump/select, turbo/cancel, item/random), Start on 3 (pause), Back on 4 (exit), Y 5, shoulders 6-7, triggers 8-9, stick clicks 10-11, the D-pad on hat 0 and the sticks on axes 0-3, so the upstream joystick defaults land on those buttons. Guide quits the game. A D-pad on buttons (as SDL reports every Android pad), on a hat or on axes all become hat 0. At launch the controllers go to players first and other joysticks only when there is no controller. Pads also hot-plug: one connected later is opened and translated when SDL reports it (Android polls every 3 s) and takes the first free joystick index, so a pad that reconnects gets its index and player back; once no match is on, the players are reassigned by the launch rules above, as if the game had been launched with the pads now connected. A removed pad's player keeps the pad's index until something else is connected. Recordings hold the translated events and replays never translate, so they replay as before; a hot-plug is a `jadd`/`jremove` line (`REPLAY.md`). `SMW_NO_KEYBOARD=1` (the muOS launcher) leaves the keyboard sets out of that assignment and turns the remaining human players into bots.
- Menus: the first keyboard player may drive menus even when it is not player 1 (upstream: only player 1), and player 1's keyboard fallback in menus is off while another player has those keys.
- Web: binding a control in the Controls menu does not block. Upstream's `MI_InputControlField::SendInput` skips `SDL_WaitEvent` under `__EMSCRIPTEN__` but keeps looping, which hangs the page (an upstream bug). The field reads each frame's polled events instead and binds the first that fits.
- Web: the main menu has the native layout (Options and Controls side by side, Exit below), so replays navigate it the same way in every build. Upstream's web build stacks Options over Controls and has no Exit. On the web, Exit ends the session (settings and the recording are saved, and the page shows its game-over overlay). Escape on the main menu still does nothing there, since a page cannot close its tab.
- Web: a standard-mapping gamepad's D-pad (browser buttons 12-15) also sends hat 0, as desktop SDL reports it. See `REPLAY.md`, Recordings.
- Touch controls (`web/touch.js`) are page-side: they dispatch player 1's default key events, so the game is unchanged and a touch session records and replays as keyboard input. Rebinding player 1's keys leaves the touch controls on the old keys. A floating stick (`Stick` button, remembered in `localStorage`) can replace the D-pad.
- On-screen keyboard (`MI_TextField`): a text field opened with a pad button or a mouse click, or any field in an Android touch session, draws a letter grid over the menu (digits, letters, `-,./` and their shifted forms, Shift, Space, Del, Done), below the field or above it for a field in the lower half. The D-pad moves, A presses a key, and B erases (or leaves an empty field); a character typed on a keyboard closes the grid and types as before. Keys the field disallows are blank. Outside an Android touch session a field opened from a keyboard key never shows it, so keyboard play and the web page's touch input (below) are unchanged. Upstream has no way to type without a keyboard. `osk_pad` replays it.
- Web text entry: while a text field is being edited, `MI_TextField` tells the page where it is and what it holds (`Module.onTextField`, web build only). On a touch screen `web/textinput.js` puts an input over the field, which opens the on-screen keyboard, and turns what is typed into the key events a keyboard sends (Shift held for capitals and symbols, Backspace, Enter, Escape), so the field, recordings and replays see ordinary key input. Desktop pages type straight into the game as before.
- The splash screen ignores Start, Back and Random until the game data has loaded (`gs_splash_screen.rs`). Upstream opens the menus at a press in its first two frames, before `load_game_data()`, and the port then dereferences the menu graphics that are not loaded yet; a quick tap after Play in the browser did that.
- Replays apply the replayed keys to the keyboard state a text field reads for Shift (`harness::keyboard_state`), so a recording that typed capitals or symbols replays them. The C++ harness pushes key events without that state and types them lowercase (`text_shift`).
- Android touch controls (`touch.rs`, `SMW_TOUCH=1` from the manifest): the game draws the web build's controls, with the same D-pad or floating-stick choice, beside the 4:3 picture and turns fingers into player 1's default key events at the frame start, so recordings stay ordinary key input. With no pad at launch they are player 1 ahead of the pads; otherwise they follow the pads. The keyboard sets get no other player and the rest are bots. A recording marks a touch session with `#@ touch=1`, so the replay assigns players the same way. Details in `android/README.md`.
- Replays ignore connected pads: natively, `--replay` and the harness set the `SDL_JOYSTICK_HIDAPI`, `SDL_JOYSTICK_MFI` and `SDL_JOYSTICK_IOKIT` hints to 0, leaving only the replay's virtual joysticks. The browser's SDL has no virtual joysticks, so a browser replay opens no pads and takes the joystick count from the replay; its events carry the device index the game binds, so pad sessions can be watched in the browser.
- The Rust harness records and replays axes and buttons 0-63; a browser recording that uses axis 6+ or button 16+ does not replay on the C++ harness.
- Native builds skip `SDL_SetSurfaceRLE` (`gfx::rle_enabled`); the web build keeps it, and `SMW_RLE=0`/`1` overrides. Through sdl2-compat RLE costs 8-16x CPU per frame (`sdl2-compat-rle.md`) and draws map foreground layers' magenta colour key opaque (`sdl2-compat-convert-blend.md`). Game state is the same either way. The reference is built with `-DSMW_NO_RLE=ON` to match, and the web build (real SDL2, RLE on) matches the same goldens.
- A player removed mid-match (e.g. the losers at a Capture the Flag game over) no longer leaves a thrown flag's `owner_throw` dangling: `clean_dead_players` clears it, so the flag scores for nobody. Upstream reads freed memory there, which differs between allocators (native and web diverged on `tools/segment_replays/tour_long.txt`; `UPSTREAM_BACKLOG.md` M8).
- Trigonometry is correctly rounded: the game's `sin`, `cos` and `atan2` come from a Rust port of CORE-MATH's `sinf`, `cosf` and `atan2f` (`crates/smw-core/src/common/math/trig.rs`, MIT), and the reference's harness build links the same C files, so native (macOS, Linux) and web builds compute the same game state. Upstream calls the platform libm, which rounds differently per platform. Against the earlier goldens only `replays_sweep/gg_boo_rondell` and `jjames_clocks_on_fire` changed (one frame each, a player's `fy` in the fourth decimal); they were regenerated from the new reference.
- Netplay works in the browser (upstream's web build is `NO_NETWORK` and disables Multiplayer). A WebSocket network layer carries ENet's connections to `smw_relay` (`RELAY.md`), the game host skips NAT punching, and skins and maps compress with flate2's Rust backend (miniz_oxide), as in the native builds. Browser and native clients cannot play together.
- Android ships `data/` in the APK and copies it to the app's external files directory on the first launch after an install or update; upstream's port reads it from `$EXTERNAL_STORAGE/supermariowar/data`, copied there by hand. Settings go to that files directory, upstream's settings directory on Android (`android/README.md`).

## Netplay deviations

- The game host decides every random outcome that changes a net game. Upstream, every client rolls them from its own copy of the shared RNG. The copies stay in step only while every client makes the same draws; one missed draw (a joiner whose replay of the host's map collision misses a block, a death one client did not see) and every later block, enemy, card, coin spot, hazard timer and respawn point differs. `tools/ref/net_game_blocks` shows it between two C++ clients. `crates/smw-core/src/smw/net_random.rs` lists the sites: block contents, frenzy cards, stomp and survival enemies, collection cards, greed coin drops, relocations (coins, cards, eggs, flags, flag bases, phanto keys, domination areas, hill zones, yoshis, secret powerups), flag base, race goal and phanto wandering, pirhana and cannon timers, respawn points, warp exits, podobo rain, POW kill order, mystery mushroom swaps, bullet bill powerups, held shells breaking, secrets, throw box items, star and tag reassignment, star timeouts, bombs and random-style boomerangs.
  - The host runs each site with the RNG recording its draws and sends `NET_G2P_RANDOM_EVENT` (93: site, object ID context, arguments, draws; placements, and new frenzy and collection cards, whose spawn points keep away from the cards a joiner holds, also carry the result). A joiner that got `NET_G2P_HOST_DECIDES_RANDOM` (92) after the sync never runs a site itself: it replays the host's with the host's draws a few frames later. Objects made during setup and inside events get matching `iNetworkID`s (unused upstream), so events can name them. A block waits until the joiner's copy stops bouncing, and a block the joiner never saw hit turns used. A joiner's player that waits 90 frames for a respawn or warp exit the host never sends picks its own. Hazards wait, and relocated objects wait out of reach, until the host's result arrives.
  - Both package types are new and the protocol version is unchanged: a C++ joiner ignores them and rolls as before, and a Rust joiner of a C++ host never hears from the host and rolls as before, so only Rust-to-Rust games (native or browser) match. The block-only packages 90 and 91 of the previous build are gone; both clients need this build.
  - Still per client, as upstream: eyecandy, and the item a view block shows while it cycles (cosmetic: the host still decides what it releases). CPU players do not exist in net games.
- The game host decides deaths, scores and the end of a net game (`crates/smw-core/src/smw/net_outcomes.rs`). Upstream, every client kills players, changes scores, removes teams and ends the match from its own collisions, so a match can end on one client first, with another winner or other scores. Kills (`player_killed_player`, `CPlayer::killed_player`, `kill_player_map_hazard`), team and player removals and the final score board are `NET_G2P_RANDOM_EVENT`s: a joiner never decides them and replays the host's, and a victim the joiner still had spawning or protected dies anyway. At the end of every frame whose scores, subscores or game end changed, the host sends them all; a joiner ignores its own score changes outside the host's events and takes its game over and winner only from the host. A joiner's deaths therefore show a few frames late. Same compatibility as the random outcomes: a C++ client on either side keeps the upstream behaviour.
  - Still per client: powerup and item pickups, shields, invincibility and other player state that only matters through the deaths the host decides; tag and chicken handover between players; carried items and projectiles; zone ownership in domination and king of the hill (their scores come from the host); positions (corrected by the host's game state, as upstream).
- Game packets name players by global ID, not `players` index (upstream indexes the vector, which a client that ended its game first has already shortened).
- The game host rolls a net game's random game mode settings (coin count, classic death style and scoring, and so on) once, at the sync, and sends them to the joiners as `NET_NOTICE_GAMEMODESETTINGS` before `NET_G2P_SYNC`. Upstream, every client rolls its own when the match starts (`GSMenu`, marked "TODO: set from network"), so two clients could play a match by different rules. When the match starts, every client applies the host's settings and reseeds the shared RNG with the sync's seed again, so setup draws in step whatever the menus drew since the sync.
- A client records the lobby's `NET_RESPONSE_CONNECT_OK` before it sends its skin. Upstream records it after, and the Servers menu moves on only if the skin went out no earlier than the reply, so a millisecond tick between the two left the menu waiting forever. `tools/ref/net_connect_stress.sh` connects 20 times on a clock that ticks on every read.
- No client plays gameplay frame 1 before every client has loaded the match. Upstream, each client starts as soon as its own `StartGame` load finishes, so a client that loads faster runs ahead and draws the other players at the origin until their first game state arrives. Each joiner sends `NET_P2G_LOADED` (94) when its first gameplay frame comes up, and waits; the host waits for every connected joiner, then sends `NET_G2P_GO` (95) and starts. The host gives up waiting after 5 s and a joiner after 10 s, so a dead peer cannot hang the game. A joiner also leaves remote players where setup put them until the host's first game state arrives.
- Native netplay with the C++ client is no longer supported: the Rust host decides random outcomes, deaths, scores and mode settings, and a C++ client on either side plays its own copy. Only Rust-to-Rust games (native or browser) stay in sync.
