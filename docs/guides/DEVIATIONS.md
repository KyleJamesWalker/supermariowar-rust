# Deviations from the C++

Where this port behaves differently from upstream [Super Mario War](https://github.com/mmatyas/supermariowar) on purpose, and the upstream bugs it still reproduces. `tools/cpp_divergences.txt` lists the replays these change.

## Known C++ issues

- Upstream `5c979393` gave hazard and platform drawing an explicit destination, but the hazards and platform shadows drawn by position in map thumbnails still go to `blitdest`, so thumbnails lack them. The port reproduces this.
- `RandomNumberGenerator::getBoolean(scaleMax, positiveThreshold)` (`get_boolean_threshold`) asserts `positiveThreshold < scaleMax && positiveThreshold >= 0` (`random_number_generator.rs:43`, a `debug_assert!` port of the C++ `assert`). Replay `opt_gameplay` trips it at frame 1209 in a release build with debug assertions. The C++ has the same assert, compiled out in the Release reference, so a debug C++ build would fail it too; the caller passing the bad range is not yet traced.
- The level editor draws a platform's hover preview at `event.button.x/y` after its poll loop, a stale event. SDL2 leaves its poll sentinel there and sdl2-compat the last real event. The editors keep the last `InputEvent` (`EditorEvent`, `editor_event.rs`), whose accessors read SDL2's union fields for any event type, so the post-loop event matches sdl2-compat, which recorded the goldens, on every backend.

## Deliberate deviations from the C++

Since phase 7 every golden comes from the Rust build. `tools/cpp_divergences.txt` lists the replays whose output differs from the C++ reference because of these deviations, which CI reports without failing.

- Fixed tick: the game advances `TICKS_PER_SECOND` (60) ticks per second of wall time on every platform and presents once after the ticks each loop runs, catching up at most 5 ticks (`paced_frame` in `main.rs`; the web loop the same). Upstream's frame rate was its game speed, paced by `framelimiter` ms of sleep per frame: nominally 62.5, measured 58.8 on an M-series Mac, and 60 on a 60 Hz handheld whose present blocks on vsync. Replays are counted in ticks and run one tick per present, so their dumps are unchanged. The netplay protocol is 0.7, since every client must run at the same tick rate and the same per-tick physics.
- Game speed at 60 ticks: every per-tick velocity, acceleration and duration from the 16 ms original is scaled to the 60 Hz tick (`vel`, `acc` and `ticks` in `global_constants.rs`), so motion and timers take the same wall time as at the nominal 62.5 frames per second. Durations labelled in seconds count `TICKS_PER_SECOND` per second. Options, world and tour files keep the original frame counts and convert on load and save; map files keep their platform and hazard speeds, converted where the objects are built. Animation periods under 10 ticks keep their tick counts. `tools/speed_probe.py` compares positions over wall time against a 62.5 Hz build. The Graphics Options "Frame Limit" setting is now "Frame Rate" (below).
- Interpolated rendering: gameplay records its screen writes (`common/gfx/display_list.rs`), tagged with the player, object, eyecandy or platform that drew them, and still draws each tick exactly as before. When presents run faster than ticks (vsync on a 120 Hz screen, `requestAnimationFrame` in the browser), the frames between ticks render from the last two records, each owned write placed between its two positions; a move over 48 px (wrap, warp, respawn) snaps. These frames are display-only, so simulation, replays and netplay never see them. A source surface the draw changes after using it (the map background, which animated tiles redraw) is copied first. `SMW_CHECK_DISPLAY_LIST=1` checks that every gameplay frame re-renders exactly from its record; CI runs it over the replays (`tools/display_list_check.py`). Vsync is on except under `SMW_VSYNC=0`, uncapped replays, `SMW_PRESENT_HZ` and SDL's dummy and offscreen drivers; `SMW_INTERPOLATE=0` turns interpolation off.
- Frame Rate (Graphics Options, upstream's "Frame Limit" slot in the options file): Display presents every refresh with vsync; 30, 40, 45, 60, 90, 120 or 144 present at most that often. The game still ticks at 60. While interpolating, a gameplay tick records its draw without drawing it, and only presented frames render pixels, so a lower rate saves power: 30 s of 4-CPU frenzy as live input took a median 1.46 s of CPU at 30 fps, 2.11 s at 60 and 3.35 s at 120 on an M-series Mac, against 2.31 s for the 16 ms frame limiter. A frame showing the pause or exit dialog is drawn as before. Upstream's frame limiter values (milliseconds) read as Display. F1 shows the last second's ticks and presents in the bottom left corner (upstream's `showfps`, whose drawing was never ported).
- All-CPU games continue on their own: when every player is a CPU, the winner screen, the bonus wheel, the tour stop and the tour and world scoreboards press Enter after three seconds (`auto_advance.rs`). The press goes through the platform's event queue, so a recording keeps it and a replay never adds its own.
- Menu taps: a touch or left click inside the picture is an `InputEvent::Tap` in 640x480 coordinates, recorded as `<frame> tap <x> <y>`. It goes through upstream's `UI_Menu::mouse_click`, continues past the title screen, and on the Players row and team select (which had no mouse handling) steps a player's control, toggles ready and presses Continue. The cursor shows outside matches. `menu_tap` replays it.
- Stick and D-pad are one control: on a joystick, a binding to a stick 1 direction also fires from the same hat direction and vice versa, in game and in menus (`CPlayerInput::update`). Upstream reads only the bound one, and its defaults bind the stick, so a D-pad-only pad did nothing.
- Players get inputs at every launch (`assign_inputs`, `main.rs`): connected joysticks first, then the right keyboard set (player 1's keyboard bindings), then the left one (player 2's); those players become human. 1 pad: P1 pad, P2 right, P3 left; 2 pads: P1-2 pads, P3 right, P4 left; 3: P4 right; 4: all pads. While the page's touch controls are on, the right keyboard set (the keys they press) goes to player 1 ahead of the joysticks. The first launch with joysticks saves the players' `playercontrol` to `pad_players.txt` in the settings directory; the next launch without joysticks restores it, sets every player back to their own keyboard set, saves the settings and deletes the file. Without that file (no pad history) a launch with no joystick keeps the saved assignment, as upstream. A joystick's bindings belong to it (`inputConfiguration[pad][1]`), so they follow it to whichever player has it; switching a player to the keyboard in Controls takes the first keyboard set no other player has.
- Game controllers (`pad.rs`, on everywhere since phase 7; `SMW_PAD_TRANSLATE=0` turns it off and reads pads as upstream): a joystick SDL has a game-controller mapping for (its database, `SDL_GAMECONTROLLERCONFIG`, or a built-in mapping for muOS's `muOS-Keys`) is read through that mapping. Its raw joystick events are renumbered through the mapping's binds into a fixed layout (inputs the mapping leaves out are dropped): A, B, X on buttons 0-2 (jump/select, turbo/cancel, item/random), Start on 3 (pause), Back on 4 (exit), Y 5, shoulders 6-7, triggers 8-9, stick clicks 10-11, the D-pad on hat 0 and the sticks on axes 0-3, so the upstream joystick defaults land on those buttons. Guide opens a Quit Game dialog, Yes or No (`quit_dialog.rs`); in a match it is the exit dialog, and Yes quits. A D-pad on buttons (as SDL reports every Android pad), on a hat or on axes all become hat 0. At launch the controllers go to players first and other joysticks only when there is no controller. Pads also hot-plug in every live session: one connected later is opened and translated when SDL reports it (Android polls every 3 s) and takes the first free joystick index, so a pad that reconnects gets its index and player back; once no match is on, the players are reassigned by the launch rules above, as if the game had been launched with the pads now connected. Team select takes in the players a hot-plug switches on or off (those already there keep their ready state), and in the game settings menu the teams are rebuilt; a player switched on any later sits the next game out instead of joining without a team. A removed pad's player keeps the pad's index until something else is connected. Recordings hold the translated events and replays never translate, so they replay as before; a hot-plug is a `jadd`/`jremove` line (`REPLAY.md`). `SMW_NO_KEYBOARD=1` (the muOS launcher) leaves the keyboard sets out of that assignment and turns the remaining human players into bots.
- Menus: the first keyboard player may drive menus even when it is not player 1 (upstream: only player 1), and player 1's keyboard fallback in menus is off while another player has those keys.
- Web: binding a control in the Controls menu does not block. Upstream's `MI_InputControlField::SendInput` skips `SDL_WaitEvent` under `__EMSCRIPTEN__` but keeps looping, which hangs the page (an upstream bug). The field reads each frame's polled events instead and binds the first that fits.
- Web: the main menu has the native layout (Options and Controls side by side, Exit below), so replays navigate it the same way in every build. Upstream's web build stacks Options over Controls and has no Exit. On the web, Exit ends the session (settings and the recording are saved, and the page shows its game-over overlay). Escape on the main menu still does nothing there, since a page cannot close its tab.
- Web: a standard-mapping gamepad's D-pad (browser buttons 12-15) also sends hat 0, as desktop SDL reports it. See `REPLAY.md`, Recordings.
- Options > Controls names each pad's family ("Xbox controller", "PlayStation controller", "Nintendo controller", "Controller") from SDL's game-controller type or, in the browser, the vendor ID in `gamepad.id` (`pad_type.rs`); a pad whose name is short enough keeps it after the family. Replays show the unchanged names.
- Touch controls (`web/touch.js`) are page-side: they dispatch player 1's default key events, so the game is unchanged and a touch session records and replays as keyboard input. Rebinding player 1's keys leaves the touch controls on the old keys. A floating stick (`Stick` button, remembered in `localStorage`) can replace the D-pad.
- On-screen keyboard (`MI_TextField`): a text field opened with a pad button or a mouse click, or any field in an Android touch session, draws a letter grid over the menu (digits, letters, `-,./` and their shifted forms, Shift, Space, Del, Done), below the field or above it for a field in the lower half. The D-pad moves, A presses a key, and B erases (or leaves an empty field); a character typed on a keyboard closes the grid and types as before. Keys the field disallows are blank. Outside an Android touch session a field opened from a keyboard key never shows it, so keyboard play and the web page's touch input (below) are unchanged. Upstream has no way to type without a keyboard. `osk_pad` replays it.
- Web text entry: while a text field is being edited, `MI_TextField` tells the page where it is and what it holds (`Module.onTextField`, web build only). On a touch screen `web/textinput.js` puts an input over the field, which opens the on-screen keyboard, and turns what is typed into the key events a keyboard sends (Shift held for capitals and symbols, Backspace, Enter, Escape), so the field, recordings and replays see ordinary key input. Desktop pages type straight into the game as before.
- The splash screen ignores Start, Back and Random until the game data has loaded (`gs_splash_screen.rs`). Upstream opens the menus at a press in its first two frames, before `load_game_data()`, and the port then dereferences the menu graphics that are not loaded yet; a quick tap after Play in the browser did that.
- Replays apply the replayed keys to the keyboard state a text field reads for Shift (`harness::keyboard_state`), so a recording that typed capitals or symbols replays them. The C++ harness pushes key events without that state and types them lowercase (`text_shift`).
- Android touch controls (`touch.rs`, `SMW_TOUCH=1` from the manifest): the game draws the web build's controls, with the same D-pad or floating-stick choice, beside the 4:3 picture and turns fingers into player 1's default key events at the frame start, so recordings stay ordinary key input. With no pad at launch they are player 1 ahead of the pads; otherwise they follow the pads. The keyboard sets get no other player and the rest are bots. A recording marks a touch session with `#@ touch=1`, so the replay assigns players the same way. Details in `android/README.md`.
- Replays ignore connected pads: natively, `--replay` and the harness set the `SDL_JOYSTICK_HIDAPI`, `SDL_JOYSTICK_MFI` and `SDL_JOYSTICK_IOKIT` hints to 0, leaving only the replay's virtual joysticks. The browser's SDL has no virtual joysticks, so a browser replay opens no pads and takes the joystick count from the replay; its events carry the device index the game binds, so pad sessions can be watched in the browser.
- The Rust harness records and replays axes and buttons 0-63; a browser recording that uses axis 6+ or button 16+ does not replay on the C++ harness.
- smw-core draws on its own surfaces (`gfx/soft_surface.rs`) in every build, so SDL surface RLE no longer applies; through sdl2-compat it cost 8-16x CPU per frame (`docs/upstream/sdl2-compat-rle.md`) and drew map foreground layers' magenta colour key opaque (`docs/upstream/sdl2-compat-convert-blend.md`). The reference is built with `-DSMW_NO_RLE=ON` to match.
- A player removed mid-match (e.g. the losers at a Capture the Flag game over) no longer leaves a thrown flag's `owner_throw` dangling: `clean_dead_players` clears it, so the flag scores for nobody. Upstream reads freed memory there, which differs between allocators (native and web diverged on `tools/segment_replays/tour_long.txt`; `docs/upstream/UPSTREAM_BACKLOG.md` M8).
- Trigonometry is correctly rounded: the game's `sin`, `cos` and `atan2` come from a Rust port of CORE-MATH's `sinf`, `cosf` and `atan2f` (`crates/smw-core/src/common/math/trig.rs`, MIT), and the reference's harness build links the same C files, so native (macOS, Linux) and web builds compute the same game state. Upstream calls the platform libm, which rounds differently per platform. Against the earlier goldens only `replays_sweep/gg_boo_rondell` and `jjames_clocks_on_fire` changed (one frame each, a player's `fy` in the fourth decimal); they were regenerated from the new reference.
- Netplay works in the browser (upstream's web build is `NO_NETWORK` and disables Multiplayer). Browsers reach the lobby over WebSocket through `smw_relay` (`RELAY.md`) and play matches over WebRTC, and skins and maps compress with flate2's Rust backend (miniz_oxide), as in the native builds. Browser and native players share rooms.
- Android ships `data/` in the APK and copies it to the app's external files directory on the first launch after an install or update; upstream's port reads it from `$EXTERNAL_STORAGE/supermariowar/data`, copied there by hand. Settings go to that files directory, upstream's settings directory on Android (`android/README.md`).

## Netplay deviations

- Net matches run under GGRS rollback over WebRTC (`docs/design/NETPLAY_V2.md`, `crates/smw-core/src/smw/net_v2.rs`). Every peer runs the whole simulation from the host's match start with every player's inputs, so peers stay frame-identical. Upstream, the game host sends positions and decides map and player collisions while each client rolls its own random outcomes from its copy of the shared RNG, so one missed draw makes every later block, enemy, card and respawn point differ (`tools/ref/net_game_blocks` showed it between two C++ clients). C++ clients cannot join.
- The lobby starts a match by sending every player `NET_L2P_MATCH_ROOM` and `NET_L2P_MATCH_START` (54). The host sends its match start, the offline checkpoint plus the map file, to the joiners over WebRTC; nobody plays gameplay frame 1 before every joiner has restored it (`READY`, then the host's `GO`). Upstream's game host connection, start sync and NAT punching are gone. Protocol 0.9.
- A client can bring up to three players on its own controllers to an online room (the room menu's Players field), while a slot is free, and each player picks a team in the room with Left and Right. Upstream plays one player per client, and its online matches take the teams of the host's last local Player Select.
- Wind changes in net matches as in local ones. Upstream skips `CheckWindEvent` online, where its clients could not keep the draws in step.
- After a match every player returns to the room, which stays open; the host can change the map and mode under "Map & Mode" and start the next one. Upstream breaks the room up.
- A net game plays the host's own game mode settings, from its mode options menu as a local game does. Upstream, every client rolls random settings when the match starts (`GSMenu`, marked "TODO: set from network"), so a net game could play Classic with the Shield death style, where a stomp only costs a life and nobody dies. The host's room settings have a "Random" option, off by default, that rolls them on the host instead.
- `SMW_NET_SEED` (scenario `#@ net_seed=`) replaces the clock as the host's match seed, so a scripted net game spawns alike every run. `tools/ref/net_game_stompkill` uses it for a player-on-player stomp, and `net_game_stompkill_powerup` for a stomp on a player holding a feather (`net_maps/netplay_feather.map`).
- A client records the lobby's `NET_RESPONSE_CONNECT_OK` before it sends its skin. Upstream records it after, and the Servers menu moves on only if the skin went out no earlier than the reply, so a millisecond tick between the two left the menu waiting forever. `tools/ref/net_connect_stress.sh` connects 20 times on a clock that ticks on every read.
